# Hosted ledger integrity review
- Logged in as operator through the normal login form. On each clean installation `/work/` exposed a settlement entry, initially unposted with two balanced $17 transaction lines; all company/ledger/entry IDs changed after reset.
- A raw HTTP/1.0 posting request received 400 and left the entry unposted. Pipelining after an ordinary `Connection: close` request returned only the first response and left it unposted. A normal HTTP/1.1 posting request worked as a baseline.
- The proof at `/testbed/proof.json` dynamically captures the login CSRF token, settlement-entry detail URL, posting URL and balance-sheet URL. Its raw step sends an HTTP/1.1 request with contradictory `Content-Length: 4` and `Transfer-Encoding: chunked` headers and a zero chunk, immediately followed on the same connection by the posting GET. The service replies 400 then 302 on that connection, indicating the rejected first request did not make the connection ineligible.
- Two independent clean-reset replays of the unchanged final proof produced the same result: before raw traffic, the official detail showed an unposted, balanced $17 entry; afterward, it showed the entry posted with the balanced $17 lines. The final step reads the official balance sheet. This is a request-integrity violation, not an ordinary authorized post on a normal valid connection.
